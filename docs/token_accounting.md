# Token Accounting & Lifecycle Specification

## 1. Executive Summary & Purpose

In Statistical Process Control (SPC) applied to generative AI pipelines, total token consumption cannot be treated as a single homogeneous number. Token usage is comprised of distinct physical mechanisms:

* **Static Input Data (I):** Raw source text extracted from textbook PDF pages.
* **Prompt Engineering Overhead (X₂):** Schema instructions and framing protocols (ε_framing).
* **Process Backlog / Work-In-Progress (X₁):** Prior conversation history retained in active session memory.
* **Quality Remediation Waste (W_rework):** Additional input tokens injected during dynamic reflection rework loops.
* **Model Reasoning Effort (T):** Internal thinking and scratchpad tokens generated by reasoning models prior to yielding final output.
* **Generation Yield (O):** Clean candidate output tokens representing the accepted Markdown transformation.

This specification formalizes how each token tier is measured, how protocol boundaries are isolated, and why live multi-turn session tokens differ from serialized cache tokens.

### 2.1 The Prompt Token Invariant

For every experimental run logged in `data/main_event_log.csv`, the total prompt tokens (`W`) of the final accepted attempt strictly satisfy the **Prompt Token Invariant**:

```text
W = context_tokens + instruction_tokens + page_tokens + framing_tokens + rework_tokens
```

Where:
* **`context_tokens` (Factor X₁ WIP Buffer):** Token footprint of prior turns loaded from `.cache/session_cache.json`. In `Phase_I`, this grows with each run. In `Phase_II`, `Phase_III`, and `Phase_IV`, this is strictly `0` due to the zero-WIP daily reset policy.
* **`instruction_tokens` (Factor X₂ Schema Overhead):** Pure tokens of the task prompt template (≈ 20 tokens for `bare_prompt.md`, ≈ 380 tokens for `memory_context.md` SOP schema). Isolates the marginal cost of schema injection.
* **`page_tokens` (Input Material I):** Raw tokens contained within the extracted text of the input PDF page. Serves as a covariate check to verify uniform input size (± 10%).
* **`framing_tokens` (Protocol Framing ε):** Protocol overhead injected by the API provider's server-side chat serialization template (role tags, boundary delimiters).
* **`rework_tokens` (Remediation Overhead W_rework):** Additional input tokens injected during dynamic reflection rework loops (`final_prompt_tokens − initial_prompt_tokens` when rework cycles > 0; exactly `0` when conforming on the first pass).

### 2.2 The Total Transaction Invariant

The total transactional footprint processed across the final accepted attempt is:

```text
total_tokens = prompt_tokens + output_tokens + thinking_tokens
```

Where:
* **`output_tokens` (Generation Yield O):** Candidate tokens of the final accepted conforming Markdown output (`response.usage_metadata.candidates_token_count`).
* **`thinking_tokens` (Model Reasoning Effort T):** Cumulative model reasoning tokens generated across all attempts in the run (`response.usage_metadata.thoughts_token_count`).
* **`total_tokens` (System Transaction Footprint):** Direct sum of prompt tokens, generated output tokens, and reasoning tokens.

### 2.3 Cumulative Multi-Attempt Audit Invariant

While the CSV ledger records the final accepted state and cumulative thinking tokens, the forensic audit log (`data/logs/run_XXX_audit.json`) preserves iteration-level telemetry across all attempts:

```text
total_api_tokens = Σ prompt_tokens_i + Σ output_tokens_i + Σ thinking_tokens_i
```

## 3. Protocol Framing & Special Boundary Tokens

### 3.1 Why Raw Text Token Count ≠ API Prompt Tokens

When tokenizing raw text strings locally:

```text
local_count = instruction_tokens + page_tokens
```

However, when submitted to the Google GenAI API endpoint, the reported `prompt_token_count` is higher by **≈ 8 to 20 tokens**. This difference represents **`framing_tokens` (ε)**.

### 3.2 Chat Template Injection

Autoregressive LLMs require special boundary tokens to distinguish conversational roles (system, user, assistant). The API provider automatically wraps prompt payloads with structural control tokens when serializing messages:

```text
[Protocol Header]          ──> <|turn_start|>user
[Instruction + Page Text]  ──> Extract the core analytical synthesis...
[Turn Delimiter]           ──> <|turn_end|>
[Model Generation Header]  ──> <|turn_start|>model
```

These structural delimiter tokens constitute protocol overhead. The engine isolates this value on Attempt 0:

```text
framing_tokens = max(0, initial_prompt_tokens − (context_tokens + instruction_tokens + page_tokens))
```

### 3.3 End-of-Turn Preemption (EOS & Stop Tokens)

When the model completes document generation:
1. It emits a reserved End-of-Sequence token (such as `<|eot_id|>` or `EOS`).
2. The server-side inference engine halts decoding immediately upon encountering this token.
3. The server sets `finish_reason = "STOP"` in response metadata and **strips the control token from the returned output text**.
4. The client receives clean Markdown. No raw control or delimiter tokens are persisted into `.cache/session_cache.json` or `data/outputs/`.

## 4. Thinking Tokens: Live Chat vs. Cache Persistence

Models equipped with extended reasoning (such as `gemini-3.8-flash` or `gemini-2.5-flash`) generate internal thinking traces (`thoughts_token_count`) prior to producing visible output text.

### 4.1 Live In-Memory Accumulation (During Rework Loops)

During an active transformation with rework loops (rework count ≥ 1):
* **Attempt 0:** Model generates Thinking Trace 0 (T₀) + Draft Output 0.
* **Attempt 1:** When the corrective reflection prompt is sent within the active Python `chat` session, the API server retains Attempt 0's thinking trace in its active session context. Consequently, Attempt 1's reported `prompt_tokens` includes T₀.
* This behavior faithfully mirrors real-world interactive chat sessions and agent loops.

### 4.2 Discarding Thinking Tokens on Persistence

Once a run completes and produces a conforming artifact:
1. Only the clean conversational text turns (user prompt + accepted Markdown output) are committed to `.cache/session_cache.json`.
2. **All internal thinking traces are discarded from persisted history.**

**Why Thinking Tokens Are Discarded from History:**
1. **Context Bloat Elimination:** Thinking traces range from 800 to 4,000+ tokens per attempt. Persisting them would saturate the context window and trigger exponential latency and cost inflation.
2. **Preventing Reasoning Anchoring:** Discarded intermediate reasoning steps from previous runs could anchor or bias subsequent independent page transformations.
3. **Industry Alignment:** Modern LLM runtimes (ChatGPT, Claude, Cursor, Copilot) discard ephemeral scratchpads from multi-turn history.
